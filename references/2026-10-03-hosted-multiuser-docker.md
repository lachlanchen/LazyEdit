# Invite-only LazyEdit + AutoPublish service

This is an isolated hosted deployment with **invite-only** registration. It
can use a separate domain or the existing `edit.lazying.art` LazyEdge route.
The latter is now deployed: [account portal](https://edit.lazying.art/accounts).
The original account continues at the usual Studio URL. Its backend,
database, Pi publisher, browser profiles and logo preferences stay in place.
Only Studio's ingress adapters changed; the original backend was not restarted.
See the [public deployment and rollback handoff](2026-10-03-edit-lazyedge-hosted-deployment.md)
for the current routing, API bases, private state and acceptance results.

## User experience

1. Open the service domain and redeem a one-use invitation. Choose a username
   and a password of at least 12 characters.
2. The automatic provisioner prepares a private workspace. The account page
   updates automatically. Click **Open Studio**; a one-use, 60-second sign-in
   link establishes a host-only Studio session.
3. Click **Platform accounts**. Choose Shipinhao, Instagram, YouTube, Douyin,
   Xiaohongshu, or Bilibili. Sign in inside the embedded private browser,
   scanning the platform QR or entering verification codes as necessary.
4. Upload videos and use the existing correction, translation, pronunciation,
   grammar-colour, logo, layout, preview, and publication controls. Each user's
   Studio settings and media library are independent. Configure that user's
   logo; the service does not inherit the owner's personal asset.
5. Publish through the normal queue. The publisher uses exactly the same
   persistent platform profiles as the login screen. No Raspberry Pi is
   required: the browser publisher runs in the workspace container.

The existing scoped API/device-link flow is available at the user's API base.
On the shared domain it is `https://edit.lazying.art/workspaces/<id>`;
`GET /accounts/account` reports `apiBase`. Clients must use that base for every
API request, including login and refresh. The original owner's API base stays
`https://edit.lazying.art`. Subdomain deployments use the workspace URL.

## Why a workspace per user

The existing adapter deliberately trusts the single owner's browser with the
whole legacy library. The backend also has global settings and AutoPublish has
fixed CDP ports. Merely adding more accounts to that adapter would expose other
users' media, jobs and platform sessions.

The hosted service therefore uses one private deployment per registered user:

```text
HTTPS / existing LazyEdge ingress
  └─ account gateway (registration, sessions, exact-host routing)
       ├─ w-<opaque-id>.SERVICE → Studio adapter + LazyEdit + AutoPublish + browser
       │                         ├─ private persistent media/profile volume
       │                         └─ private PostgreSQL container and volume
       └─ next user → independent deployment with the same image
```

This reuses the mature processing/publishing code. It does not add tenant IDs
through every legacy SQL query. Each workspace has one owner; never insert
multiple users into a workspace's Studio account database.

The gateway has **no Docker socket** and cannot accept arbitrary Docker options.
A separate provisioner container reads pending registrations and applies a fixed
Compose template. It has no network interface/listener; only this trusted
controller has the Docker socket. Workspace IDs are generated by the server and validated
again before generating paths. The gateway mounts only its account registry,
not workspace bootstrap/provider files. Raw backend, publisher, VNC, CDP and
PostgreSQL ports are never host-published. The only workspace-facing listener
requires a private transport credential, then the user's Studio authentication.
noVNC HTTP **and WebSocket** access require that workspace's browser session;
WebSockets also require an exact Origin match.

## Build on a separate Docker host or workstation

Requirements: Docker Engine + Compose v2, Node 22 for initial configuration,
Linux x86-64, and enough local disk/RAM. CPU execution is the tested image
target; ARM/Pi and GPU builds are not claimed as validated.

Initialize required source submodules in a clean checkout. Do not copy external
symlink targets or local credential/config files into the image:

```bash
git submodule update --init AutoPublish furigana whisper_with_lang_detect vit-gpt2-image-captioning
docker build --target gateway -f deploy/hosted/Dockerfile -t lazyedit-gateway:local .
docker build --target provisioner -f deploy/hosted/Dockerfile -t lazyedit-provisioner:local .
docker build --target workspace -f deploy/hosted/Dockerfile -t lazyedit-workspace:local .
```

`Dockerfile.dockerignore` is an allowlist. It excludes DATA, model weights,
Git history, .env, cookies, profiles, SQLite files, logs and untracked runtime
archives. The runtime installs portable dependencies rather than importing the
workstation's conda freeze. Build the image once; users share image layers, not
writable state. Record image digests and pin them in production config.

## Operator setup

For a separate-domain installation use the commands below. The current
`edit.lazying.art` installation instead uses `--same-host`; read its deployment
handoff and do not rerun initialization against existing state.

```bash
node hosted/admin.mjs init "$HOME/.local/share/lazyedit-hosted" studio.example.com
cp deploy/hosted/providers.env.example "$HOME/.local/share/lazyedit-hosted/providers.env"
chmod 600 "$HOME/.local/share/lazyedit-hosted/providers.env"
$EDITOR "$HOME/.local/share/lazyedit-hosted/providers.env"
docker compose -f "$HOME/.local/share/lazyedit-hosted/compose.json" up -d
node hosted/admin.mjs invite "$HOME/.local/share/lazyedit-hosted"
```

The last command prints the invitation for the operator to deliver privately.
It expires in 72 hours and can be redeemed once. Passwords use salted scrypt;
opaque sessions and invitation codes are stored as hashes. Passwords are never
stored in plaintext. The registry does contain transport secrets, so back it up
as sensitive account data with restricted permissions and encryption.

Configure an AI provider before inviting users. A service-owned provider file
is copied into a workspace only at first provisioning. Per-user AI credentials
can instead be placed in that workspace's `providers.env`. Do not put a global
`TO_EMAIL` in a shared template: optional QR emails must go to the intended
workspace owner. No existing personal credentials are imported automatically.
Provider changes require an idle workspace restart; they do not mutate the
owner's existing backend or Pi.

Workspace users control their browser desktop and can read their workspace's
files. Prefer individual, restricted provider keys and per-user budgets. Do not
copy an unrestricted shared operator key into workspaces you do not trust.

The Compose deployment includes the automatic provisioner. For inspection or
a manual provisioning pass:

```bash
node hosted/admin.mjs provision "$HOME/.local/share/lazyedit-hosted"
node hosted/admin.mjs status "$HOME/.local/share/lazyedit-hosted"
```

The provisioner checks registrations every 30 seconds. The optional systemd
examples are an alternative for operators who prefer a host-side controller;
use one controller arrangement. No public API accepts Docker flags or paths.
A five-minute registry lease prevents duplicate provisioning and allows recovery
if the controller restarts midway. Reconciliation uses the same Compose project,
volumes and database password. A failed health check leaves the account `failed`;
inspect its Docker logs, run `admin.mjs retry STATE_DIR WORKSPACE_ID`, and let the
controller reconcile it.

The initial Linux deployment uses UID 1000 for both images and private state.
Run initialization as that user (the usual first Ubuntu account). Root-operated
installations must give UID 1000 access to this deployment's private state only.
The controller gets the Docker socket's host group ID at initialization. A
rootless Docker/custom socket installation requires an explicit socket-path and
group adjustment; the provided recipe assumes `/var/run/docker.sock`.

Default capacity is three workspaces, each capped at 8 GiB / two CPUs, plus a
512 MiB database. This is a capacity ceiling, not a throughput claim. Change
both the private operator `config.json` and `registry/gateway.json` consistently
before expansion. GPU allocation/scheduling is intentionally not implicit. The
portable image uses CPU Whisper small/base; quality/performance upgrades need
an explicit resource plan. Generating a large video remains compute-heavy.

## Separate-domain HTTPS / LazyEdge

The gateway publishes only `127.0.0.1:18980`. Keep the existing LazyEdge
authenticated reverse-tunnel separation: bind a new service to this loopback
port with a dedicated upstream credential and preserve the original HTTP Host,
Origin and WebSocket upgrade. Route only `studio.example.com` and
`*.studio.example.com`; arbitrary Host values are rejected by the gateway.

DNS and certificates must cover both the account domain and workspace
subdomains. Wildcard TLS typically uses DNS-01 on the existing TLS terminator;
otherwise use separately issued certificates for explicitly provisioned names.
Do not claim that an A record alone configures wildcard HTTPS. Do not share the
live Studio/LazyTunnel transport credential with this new deployment.

Direct gateway deployments ignore caller-supplied forwarding/identity headers
and throttle their immediate peer. In deployed same-host mode, ingress
authentication is mandatory; identity comes from Caddy's overwritten socket
peer through the authenticated Studio transport.

## Browser login and publishing

One X display per workspace serves its platform windows. Browsers are opened on
demand, with separate profiles for each platform beneath `/state/home/`.
Chromium is non-root; this initial container uses `--no-sandbox` within Docker
isolation because a nested Chromium sandbox is not assumed to work on every
Docker host. Containers have dropped capabilities, no-new-privileges and no
host mounts beyond their own bootstrap files. This is an invite pilot, not a
claim of hardened isolation against hostile tenants: validate browser sandbox,
network egress policy, kernel isolation and storage quotas before public signup.

The desktop is a real authenticated browser, not a stored platform password
form. Platforms may expire sessions, require QR/2FA, challenge cloud addresses,
or change their UI. Docker cannot remove those requirements. The normal long
login wait remains unchanged. Publishers log their real success evidence; no
synthetic publish is used to claim account login or platform compatibility.

Opening a new login page is refused while publication is queued/running.
Existing noVNC access remains available for completing a QR/verification gate
during publication. Users should avoid unrelated navigation while it runs.

## Durable jobs and restart policy

LazyEdit uses its per-workspace PostgreSQL queue. AutoPublish optionally uses
`AUTOPUBLISH_QUEUE_JOURNAL` to atomically persist its queue in the same user's
volume. This variable is set in Docker; legacy installations are unchanged
unless explicitly enabled.

- A queued job returns to the queue after restart.
- Done/failed jobs remain in history.
- A job interrupted while `running` becomes failed with an explicit instruction
  to check platform history. **It is not replayed automatically**, because a
  browser may have submitted just before the process stopped.
- Only terminal history is trimmed; waiting/running jobs are never evicted by
  the history limit.
- A corrupt journal fails closed and needs operator inspection.

Each workspace is serial internally. Different users can publish concurrently
in different browser profiles; they never share the Pi's global browser/queue.
The host's capacity limit bounds concurrent workspaces. Gracefully drain an
active workspace before changing its image.

## Backups, removal, and capacity

### One media store, fewer temporary files

Each workspace has one persistent `/state` volume. Studio, rendering and
AutoPublish use that same volume; the registration gateway stores no media.
The completed resumable upload is renamed into the library, not copied.
Abandoned upload parts expire through the existing upload cleanup.

For a local video **or music** publication, `LAZYEDIT_LOCAL_PACKAGE_ROOT` and
`AUTOPUBLISH_LOCAL_PACKAGE_ROOT` opt into a path-only ZIP handoff over loopback.
AutoPublish reads the existing prepared ZIP in `/state/data`; it does not
receive or save another copy of the archive. It records its SHA-256 and refuses
to publish if that package changes while queued. Hashing runs off the HTTP
event loop so status and desktop requests stay responsive.

Browser uploads still need ordinary extracted files. Those go in the exact
job's `/state/publisher/transcription_data/scratch/<job-id>` directory, which
is removed after success or failure. Startup also removes scratch for terminal
and interrupted jobs. This cleanup does not follow an arbitrary user path or
delete the canonical archive. A reviewed retry can extract the same archive
again. Queue records and evidence logs remain available.

"One copy" here means one canonical copy of each required artifact, shared by
the services. A source video, edited render and reusable ZIP are different
artifacts; the ZIP still contains the render. This change does not erase source
media, prior publication runs, corrected transcripts or audit evidence. It also
does not add broad age-based deletion of user files. Raw frame/ML caches remain
subject to their existing pipeline retention rules. Image layers are shared
across workspaces, while personal media and browser profiles are isolated.
Docker worker/database console logs rotate with bounded sizes; publication
evidence files remain separate from those console logs.

The path-only protocol is disabled by default outside Docker. Remote/Pi
delivery still uploads ZIP bytes and keeps its existing storage behaviour.

Preserve `registry/registry.sqlite` (use a SQLite backup or stop the gateway),
private bootstrap files, each Compose file, PostgreSQL backups, and workspace
volumes. Browser profiles contain login credentials; treat them as secrets.
Do not commit any of this state. `docker compose down` retains named volumes;
`down -v` deletes them and must never be used as an ordinary upgrade.

The existing upload API enforces per-file limits and available-space checks.
This pilot does not implement billing, account recovery/email verification,
hard filesystem quotas, autoscaling or a global GPU job scheduler. Monitor
storage and establish filesystem quotas before admitting untrusted tenants.
Keep the image and at most the current/previous verified release; don't copy
the host's entire model cache per user. A future read-only model cache can be
shared after separating model weights from prompts, transcripts and credentials.

## Verification

```bash
node --test hosted/test.mjs studio/test.mjs
PYTHONPATH=.:AutoPublish python -m pytest -q tests/test_local_delivery.py \
  AutoPublish/tests/test_queue_journal.py AutoPublish/tests/test_local_package.py \
  AutoPublish/tests/test_hosted_account_detection.py
```

Tests cover invitation use/capacity, separate media and queues, cookie isolation,
one-use SSO, forged headers, unknown hosts, path traversal, private worker
transport, authenticated desktop/WebSocket origins, and safe journal recovery.
Real platform publication is deliberately excluded from Docker smoke tests.
See the validation record appended after image/runtime checks.

### Initial loopback validation, 2026-10-03

Built all three Docker images and ran a disposable, loopback-only deployment
with an empty account and no real platform or AI credentials. The automatic
provisioner created a healthy private PostgreSQL/workspace pair from an
invitation redeemed through the gateway.

Verified:

- Six Node tests covering both the existing Studio adapter and hosted routing;
  twenty focused Python tests covering queue recovery, generic login detection,
  shared package storage, cleanup and existing publisher regression cases.
- Non-root runtime imports of LazyEdit and TorchCodec, healthy backend,
  publisher, authenticated Studio and private desktop.
- Upload of a two-second synthetic video through the real resumable API,
  matching SHA-256, database registration and an empty upload staging directory
  after completion. No owner media was used.
- Studio page rendered in Chromium with the test library and no severe browser
  console errors. Private noVNC returned a successful WebSocket handshake and
  real VNC protocol data; anonymous access was denied.
- Opening YouTube's sign-in page through the platform-login adapter, in an empty
  persistent profile. No Google/platform account was entered and no post was
  submitted. The existing owner's profiles were not accessed.
- A short subtitle render with English colours, Japanese furigana and Chinese
  pinyin; the rendered frame was inspected visually.
- Container replacement preserving media, database registration, an existing
  Studio session and the browser profile directory.
- A deliberately **no-target** queue request using a shared canonical ZIP:
  no second ZIP appeared under publisher storage and its scratch directory was
  removed. This is queue/storage evidence, not social-publication evidence.

The initial image exposed two portability issues that were fixed in the build:
root-owned source files with mode 0600 prevented non-root imports, and an
unconstrained TorchCodec version did not match CPU PyTorch. The explicit file
modes and compatible dependency pins are now in the Dockerfile/requirements.
UI review also caught a login-desktop iframe that was loaded only after opening
a new browser. It now connects on page load, including during a queued job's
login/verification wait. The platform shortcut sits above the bottom account
controls without covering the language selector.

Real ASR/LLM provider calls and end-to-end social submissions were not performed.
An invited pilot user still needs provider configuration, dedicated DNS/TLS,
and their own platform login. Keep those distinctions when reporting readiness.
The disposable containers and test volumes are removed after validation;
no public service was enabled by these initial checks. The live owner backend and Pi
remain on their existing deployment.

The subsequent same-domain deployment and public acceptance checks are
recorded in the [deployment handoff](2026-10-03-edit-lazyedge-hosted-deployment.md).

Dependency reference: TorchCodec must match the installed PyTorch release; the
image pins TorchCodec 0.8.0 with PyTorch 2.9.1 according to the
[official compatibility table](https://github.com/meta-pytorch/torchcodec#compatibility-with-torch-versions).
