# iOS Studio React #31: structured gateway error and request pressure

## Reproduction and cause

The iOS private beta loads the authenticated Studio web interface. Navigating
Home → Publish → Studio also reproduced its `Something went wrong` screen in
the production browser at a 390×844 viewport. The exception was:

```text
Minified React error #31; ... args[]=object with keys {code}
```

The actual HTTP response from LazyEdge was status 429:

```json
{"error":{"code":"too_many_requests"}}
```

It appeared on burn status, publication sessions, cover, video list, publish
queue, and process-status reads. Legacy React views expect `error` to be a
string. In particular, the Publish screen assigns the process-status error
directly to rendered text. A structured error therefore crashed the render
tree, rather than merely reporting a temporarily busy server.

The Studio gateway has a deliberate 12-request concurrency limit. Home and
Studio lists were preloading metadata from multiple full videos; inactive tabs
also retained requests, while remote Home unnecessarily fetched large histories
for hidden generation tools. On the 2 Mbps edge these responses remain active
long enough to crowd out editor requests.

## Fix

- `studio/web/session.js` normalizes same-origin failed JSON responses to the
  string-error contract used by existing screens. Unknown structured errors
  have a safe fallback; nested error codes/messages never become React children.
- Same-origin GETs under `/api/` and `/v1/` use four read slots. A slot is held
  until the JSON body completes, not merely until headers arrive.
- Only GETs retry transient 429/502/503/504 responses, at most twice, with a
  bounded delay. POST, PUT and DELETE are never automatically replayed. This
  must remain true for publication, processing and resumable upload mutations.
- Remote Home skips histories for tools not offered by the remote interface.
- Remote Home/Studio list videos use `preload=none` with available poster images.
  An opened player still works normally. Local Studio retains metadata preload.
- The exported app includes a small inline loading screen. It remains visible
  until React actually mounts after bundle/font loading, including the transition
  from sign-in. A long wait reveals Reload/Sign in actions. It never masks an
  already-rendered app or schedules an automatic login/reload loop.
- Authentication, the gateway concurrency limit, publisher queue, and native
  package identities remain unchanged.

## Regression checks

```sh
node --test studio/session.test.mjs studio/test.mjs
```

The regression suite reproduces React's object-child failure with the real
React renderer, checks safe display after normalization, GET recovery and retry
limits, slow-body concurrency, slot release after network rejection, unknown
error shapes, unchanged successful/external responses, 401 sign-in redirection,
and no mutation replay. The existing authentication/ownership/CSRF/idempotency
tests run alongside it.

Export and deploy via `operations.md`; only the Studio worker needs a restart.
The core LazyEdit backend and AutoPublish processes do not need restarting.
The current iOS/Android hosted beta receives this fix after closing and reopening
the app; a new native store binary is not required for this web-interface fix.

Keep screenshots, complete request traces and deployment/rollback receipts in
the private Nutstore `Share/LazyEdit/runtime` directory. The public source note
contains only the diagnostic response shape. Browser reproduction verifies the
shared UI; it is not evidence of a physical iPhone retest.
